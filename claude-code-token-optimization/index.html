01

背景：额度不是突然没的

之前每次用 Claude Code 都觉得 token 消耗贼快，但也只是隐约觉得贵。账号额度用得快时，先靠换国产模型顶一顶，能撑就撑。直到最近并行项目变多，同一个账号要同时承载更多冷启动、更多插件、更多 agent，问题才从“有点肉疼”升级成“必须查账”。

这类问题很容易误判成模型本身太贵，或者自己 prompt 写太长。但这次的原始请求里，用户输入只有 6 个 token，输出也只有 14 个 token，真正夸张的是 cache write 82619。也就是说，一次几乎没有内容的请求，花钱的大头依然在冷启动上下文。

核心判断：先不要急着换模型。先看 Claude Code 在首轮到底塞了什么，再决定该删 CLAUDE.md、插件、skills、agents、memory，还是工具 schema。
02

优化前先拿一条最小请求做基线。可以用你自己的 cc env 或导出脚本观察 Claude Code 原始 request / response，也可以从本地 transcript 和代理日志里对齐 usage 字段。

简单请求却有巨大的 cache write，通常意味着常驻系统上下文太重，优化空间也主要在这里。

03

冷启动 token 从哪里来

可以把 Claude Code 的首轮上下文理解成一张“启动菜单”。菜单越厚，哪怕你只点一杯水，也要先把整本菜单塞进模型上下文。

经验拆法：优先看全局和项目 CLAUDE.md，再看全局插件 / skills / commands，随后查全局和项目 agent，最后看 agent team、auto memory、tools 这类开关。

第一刀：CLAUDE.md、插件和 skills

CLAUDE.md 最适合用类似 caveman 的原则重写：只保留会改变模型行为的硬约束，删除历史解释、长案例、重复规则和已经被项目工具固化的流程。全局 CLAUDE.md 只放跨项目稳定规则，项目 CLAUDE.md 只放这个仓库必须知道的事实。 

find -L ~/.claude -maxdepth 6 \( -name "SKILL.md" -o -name "settings.json" -o -name "settings.local.json" \) -print 2>/dev/null | sort
find -L . -maxdepth 8 \( -name "SKILL.md" -o -name "settings.json" -o -name "settings.local.json" \) -print 2>/dev/null | sort

清理顺序建议插件优先，因为一个插件往往带多个 skill、command 和 agent。全局只是“常用工具箱”，不是“所有玩具展柜”。只服务某个项目的 skill，迁到项目级；低频但偶尔要显式调用的 skill，可以考虑加 disable-model-invocation: true，让它不再默认进入首轮可见入口。

如果要半自动处理，建议只做“列清单 + 逐项确认”，不要脚本直接 rm。每一项都基于当前项目判断：保留、迁移到项目级，或者先移动到 disabled 目录观察一段时间。 

disabled_dir=".claude-disabled/$(date +%Y%m%d-%H%M%S)"
mkdir -p "$disabled_dir"

{
  find -L ~/.claude -maxdepth 6 -name "SKILL.md" -print 2>/dev/null
  find -L . -maxdepth 8 -name "SKILL.md" -print 2>/dev/null
} | sort | while IFS= read -r skill_file; do
  skill_dir="$(dirname "$skill_file")"
  printf "\n%s\n[d]isable [s]kip [q]uit? " "$skill_dir"
  read -r answer
  case "$answer" in
    d) mv "$skill_dir" "$disabled_dir/${skill_dir//\//__}" ;;
    q) break ;;
    *) ;;
  esac
done

第二刀：agent 不要全局滥装

之前为了测试 spec-kit-agent-assign，又安装了 agency-agents 这类全局 agent。它们在特定场景有用，但如果全局常驻，就会把每个项目都变成 agent 展示厅。 

claude agents
find -L ~/.claude -maxdepth 8 -path "*/agents/*.md" -print 2>/dev/null | sort
find -L . -maxdepth 8 -path "*/agents/*.md" -print 2>/dev/null | sort

这里要特别注意“不能遗漏全局目录”。如果某个 agent 只给一个项目用，就迁到项目 .claude/agents/；如果只是实验遗留，就删除或先移到 disabled 目录。清完之后，token 从 56.5K 继续降到 42.0K。

第三刀和第四刀：agent team、auto memory

实验性的 agent team 和 auto memory 不应该因为“也许以后会用”而全局开启。明确当前项目不用，就关掉；某个项目确实要用，就只在那个项目启用。这样既能保留能力，又不让每个冷启动为低频能力买单。

第五刀：裁剪 tools schema

官方 CLI 文档里，--disallowedTools 的关键点不是“少弹权限提示”，而是这些工具会从模型上下文里移除，无法使用。这个区别很重要：--allowedTools 主要解决免确认，--tools 和 --disallowedTools 才更适合做上下文裁剪。 

alias claude='claude --disallowedTools "CronCreate" "CronDelete" "CronList" "ScheduleWakeup" "EnterWorktree" "ExitWorktree" "NotebookEdit" "TaskOutput" "TaskStop"'

如果你确定日常不用 Agent、AskUserQuestion、Plan Mode 一类能力，可以再准备一个更瘦的 alias，而不是直接覆盖所有场景。 

alias claude-slim='claude --disallowedTools "CronCreate" "CronDelete" "CronList" "ScheduleWakeup" "EnterWorktree" "ExitWorktree" "NotebookEdit" "TaskOutput" "TaskStop" "Agent" "AskUserQuestion" "EnterPlanMode" "ExitPlanMode"'
对脚本化一次性任务，还可以关注官方 --bare：它会跳过 hooks、skills、plugins、MCP、auto memory 和 CLAUDE.md 的自动发现，让 headless 调用更轻。但这更适合自动化，不适合直接替代日常交互会话。

第六个注意点：别忽略 5 分钟缓存有效期

还有一个很容易被忽略的消耗点：prompt cache 默认只有 5 分钟有效期。两次对话间隔超过 5 分钟后，下一轮很可能不再是 cache read，而是重新 cache write。如果这时会话已经很长，就等于把一大段上下文重新写入缓存。

SUCCESS
第一次对话 · “你好！有什么需要帮忙的吗?” youdao-cc · claude-sonnet-4-6
2026/5/9 09:16:21 I3 / O45 CW 30.6K / CR0 · 5m
间隔超过 5 分钟
SUCCESS
第二次对话 · “你好！有什么我可以帮你的吗?” youdao-cc · claude-sonnet-4-6
2026/5/9 09:23:05 I3 / O18 CW 30.6K / CR0 · 5m

所以离开超过 5 分钟再回来，尤其是长对话场景，最好先新开会话，或者先运行 /compact 压缩会话。不是每次都必须这么做，但当你看到 CR 0 且 CW 又重新变大时，就说明这轮又在付“重建上下文”的钱。

05

成本账：最后便宜了接近 68%

下面按你给出的 Opus 4.7 计价基准计算：普通输入 $5 / 1M，输出 $25 / 1M，5 分钟缓存写入 $6.25 / 1M。不同模型和不同时段价格可能变化，实际结算以当时账单为准。

原始费用 = 6 × 5 / 1M + 14 × 25 / 1M + 82619 × 6.25 / 1M = $0.516749
优化后费用 = 6 × 5 / 1M + 20 × 25 / 1M + 26585 × 6.25 / 1M = $0.166686
$0.5167 原始单次请求估算费用
$0.1667 第五轮后单次请求估算费用
$0.3501 单次节约，比例 67.74%

这次能省这么多，并不说明每个人都有同等空间。它更像一个反面教材：我把 skills 和 agents 全局安装、长期不卸载，导致每个项目冷启动都背着一整套历史包袱。优化的本质，是把“全局默认加载”改回“按项目、按场景、按需启用”。

06

可复用流程：以后别靠记忆清理

手工优化最怕两件事：第一次很爽，第二次忘了；现在省了很多，过两周又装回一堆。建议把这套流程变成固定体检。

先测最小请求基线记录 input、output、cache write、cache read、total，尤其关注冷启动的 cache write。
压缩 CLAUDE.md全局只放跨项目规则，项目只放仓库事实；长解释和示例迁到文档，不常驻。
插件优先清理先看插件，再看插件带出来的 skill、command、agent；低频能力不要全局启用。
agent 分层管理全局只留高频通用 agent，项目特化 agent 放项目目录，实验遗留及时移走。
关闭不需要的实验能力agent team、auto memory 等能力按项目开启，不用就关。
准备多档 alias默认 alias 保留常用能力，slim alias 裁剪冷门 tools，脚本任务再考虑 --bare。
盯住缓存有效期离开超过 5 分钟再回来，长会话优先新开或 /compact，避免整段上下文重新 cache write。
07

工具化落地：project-token-insights

这里不是一个“以后再做”的规划，而是这次排查真正值得收束的地方：最开始靠自己翻 usage、看 settings、找 CLAUDE.md、清 plugins / skills / agents；最后把这套手工经验沉淀成了 project-token-insights，让项目可以自动查、自动出报告、自动提醒。

升华点：这次优化解决的是一个账号的消耗问题；工具化之后，解决的是每个项目都能持续自检的问题。从“我知道该怎么排查”，变成“项目自己能给出排查报告，并在高成本动作发生前提醒我”。

从人工翻文件到自动扫描

以前要自己查全局 / 项目 CLAUDE.md、插件 manifest、skill metadata、agent frontmatter、auto memory 和工具 schema；现在脚本会自动重建首轮 token 组成。

从体感判断到 JSONL 校准

读取当前项目对应 transcript，用冷启动首轮 cache_creation_input_tokens 的 p50 / p75 对照估算结果，避免只凭体感判断。

从口头经验到中文报告

直接输出中文优化报告，按 2.1 到 2.6 列出大头组件、未使用 agent、agent team、auto memory、tools、重复规则和对应操作。

从事后复盘到 hooks 监控

hook 已经可以在首轮超过预算，或 5 分钟 prompt cache 可能过期时，在下一次提交前提醒，避免默默重新烧一轮。

安装：从 GitHub 拉到 Claude Code skills

工具已经上传到 github.com/xymelon/skills。如果还没安装，可以把仓库拉到本地 skills 目录，再给 project-token-insights 建一个入口。 

mkdir -p ~/.claude/skills

if [ ! -d ~/.claude/skills/xymelon-skills ]; then
  git clone --depth 1 https://github.com/xymelon/skills.git ~/.claude/skills/xymelon-skills
else
  git -C ~/.claude/skills/xymelon-skills pull --ff-only
fi

if [ ! -e ~/.claude/skills/project-token-insights ]; then
  ln -s ~/.claude/skills/xymelon-skills/project-token-insights ~/.claude/skills/project-token-insights
fi

检查：先跑一次项目体检

安装后可以直接在 Claude Code 里调用 /project-token-insights。如果只是想先验证脚本，也可以在项目根目录手动跑下面两步：第一步生成首轮组件基线，第二步生成中文优化报告。 

python3 ~/.claude/skills/project-token-insights/scripts/first_turn_breakdown.py --pretty
python3 ~/.claude/skills/project-token-insights/scripts/optimization_report.py

报告会落到当前项目的 .project-token-insights/optimization-report.md，里面会列出大头组件、置信度、预计节省和建议操作。这样下次遇到 token 异常，不必重新凭记忆翻目录，而是先让工具给出一份可对照的体检结果。

安装 hooks：把检查变成提醒

hooks 是这套工具真正从“报告”走向“监控”的部分。安装前先看状态；确认后安装到当前项目。它只写当前项目的 .claude/settings.local.json 和 .project-token-insights/hooks/，安装后重启 Claude Code 让 hook 生效。 

python3 ~/.claude/skills/project-token-insights/scripts/install_hooks.py --status
python3 ~/.claude/skills/project-token-insights/scripts/install_hooks.py

# 如果只想先盯首轮超限
python3 ~/.claude/skills/project-token-insights/scripts/install_hooks.py --only first-turn

最后的结论就更清楚了：优化 Claude Code token，不只是把能力越关越少，而是把默认加载从“我可能会用”收敛成“这个项目马上会用”，再把这套判断固化成工具和 hooks。全局越克制，项目越清晰，冷启动就越轻；工具越早提醒，下一次踩坑就越少。
